# T019 — Failing tests for credential hashing and session expiry

**Task**: Write failing tests for credential hashing and session expiry in
`backend/tests/unit/test_auth_service.py`.

## What problem is this solving?

FR-048 requires sign-in. FR-079 is the interesting one:

> Credential storage, session handling, and secret management MUST be built to a standard that would
> remain sound under public exposure. No measure may rely on the local-only assumption — stored
> credentials are hashed, sessions expire and can be invalidated, and secrets never appear in
> responses, logs, or anything the client can read.

The reasoning behind that requirement is a cost argument, set out in the spec's Assumptions. Transport
security and abuse protection cost real money and can be added later without touching code, so they
are deferred (FR-081). Credential storage cannot: changing how passwords are stored *after* a
credential exists is a migration, not an edit. So the cheap-now, expensive-later measures are built
now, and this is the test file that pins them.

These tests therefore assert properties that would matter on a hostile network, not merely that
signing in works.

## Two decisions the tests encode

### Hashing with `hashlib.scrypt`, not bcrypt or argon2

The constitution's Technology and Data Constraints fix the committed stack and say plainly that
"introducing a dependency outside this list requires the amendment procedure". `bcrypt`, `passlib`,
and `argon2-cffi` are all outside it. Amending the constitution to add a password-hashing library is a
lot of ceremony for a single-user tool.

`hashlib.scrypt` is in the Python standard library and is a real memory-hard password KDF — not a bare
hash. It needs no new dependency, so no amendment, and it is genuinely the right tool rather than a
workaround. Cost parameters are stored *in* the encoded hash:

```text
scrypt$16384$8$1$<salt base64>$<hash base64>
```

Storing them means the cost can be raised later without invalidating a credential hashed under the old
settings — a test asserts the format carries them.

### Sessions in Redis, keyed by a hash of the token

Redis gives expiry (TTL) and invalidation (`DEL`) natively, which are exactly the two properties
FR-079 asks for.

**This is a judgment call worth flagging.** The constitution says Redis "MUST be treated as
reconstructible from PostgreSQL, so no data may exist only in Redis". A session does live only in
Redis. The argument that this is consistent rather than a violation: that rule exists to protect the
*corpus* — the collected material that cannot be re-fetched, which is why R14 treats it as
irreplaceable. A session is the definition of reconstructible; losing every session costs one sign-in.
Putting sessions in PostgreSQL would mean a table and a migration that no task in this phase allocates,
to protect data whose loss is a minor inconvenience.

A reviewer could reasonably disagree, which is why it is recorded here rather than left implicit.

The second half — **only a hash of the token is stored** — is the part that matters under FR-079. If a
Redis dump or a backup leaks, what leaks is not a set of usable sessions. The tokens themselves are 32
random bytes, so a plain SHA-256 is right here; a slow KDF protects low-entropy secrets, and these are
not low-entropy.

## What the tests cover

**Hashing** — a hash verifies against its own password; a wrong password does not; the same password
hashes differently every time (random salt, which is what defeats precomputed tables); the plaintext
never appears in the output; and six flavours of malformed stored hash are rejected as "wrong
password" rather than raising. That last group matters because a hand-edited `.env` must fail closed,
not produce a traceback describing how credentials are stored.

**Authentication fails closed with no credential configured.** A fresh checkout has no
`AUTH_PASSWORD_HASH`. The dangerous reading of "no password set" is "no password required". A test
pins the opposite.

**Sessions** — lookup by token, unknown tokens resolve to nothing, tokens are distinct and long, and
the raw token is absent from both the keys and the values in the store.

**Expiry is asserted from both sides.** One test advances the clock past the TTL and expects the
session to be gone; its companion advances to just before and expects it to still work. Without the
second, a function that always returned `None` would pass.

**Expiry is enforced by the application, not only by Redis.** One test re-stores the session entry
with no TTL at all — simulating a store that lost its expiry bookkeeping — advances the clock, and
still expects a refusal. Redis TTL is what stops expired sessions accumulating; it is not what decides
whether a session is valid.

**Invalidation** — a session can be killed before it expires (sign-out, and the control that matters
when a token is believed compromised), and "invalidate everything" does not touch unrelated keys.
Sessions share Redis with the Reddit cache and the rate limiter, so a sign-out-everywhere implemented
as a flush would throw away collected material's cache.

**Two small properties from elsewhere**: timestamps are UTC (Constitution V), and a `Session` does not
print its own token in `repr()`, so an exception handler or debug line cannot spill a live credential
into a log (FR-079 again).

## Determinism

No test sleeps. `tests/conftest.py` — new in this task — provides `FakeRedis` and a `FakeClock` that
moves only when a test moves it. Constitution IV forbids both a networked test and a nondeterministic
one, and `sleep`-based expiry testing is both slow and flaky.

`FakeRedis` implements only the commands this project uses. That is deliberate: an incomplete fake
that raises on an unimplemented command is safer than a plausible one that quietly disagrees with the
real server. It is in `conftest.py` rather than this file because T022's rate limiter needs the same
boundary mocked, and Constitution IV asks for shared fixtures there.
