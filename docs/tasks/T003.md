# T003 — Configure ruff lint and format rules

**Task**: Configure ruff lint and format rules in `backend/pyproject.toml`

## What problem is this solving?

When multiple people (or you, at 11pm vs. 9am) write Python code, everyone has slightly different
habits — some use single quotes, some double; some sort their imports alphabetically, some don't;
some forget to add type hints. Left unchecked, a codebase turns into a mess of inconsistent styles,
which makes it harder to read and easier to introduce bugs.

Two tools fix this:

- A **linter** reads your code and flags problems — unused imports, missing type hints, stray
  `print()` statements — without necessarily running the code.
- A **formatter** automatically rewrites your code to a consistent style — spacing, quote style, line
  length — so nobody argues about style in code review.

**Ruff** is a single fast tool that does both jobs (it replaces what used to be two or three separate
tools: flake8 for linting, isort for import sorting, black for formatting).

## What is `pyproject.toml`?

It's a standard configuration file for Python projects — basically a settings file where tools like
ruff, pytest, etc. look for their configuration. `backend/pyproject.toml` has a `[tool.ruff]` section
telling ruff exactly what rules to enforce for this project.

## What rules were turned on, and why?

Each rule set is a short code:

| Code | What it catches | Why it matters here |
|---|---|---|
| `E`, `W`, `F` | Basic Python mistakes (unused variables, syntax-adjacent issues) | Baseline correctness |
| `I` | Imports not sorted/grouped properly | Keeps every file's import block predictable |
| `UP` | Old-style Python that has a newer, cleaner equivalent | Keeps code modern for Python 3.11 |
| `B` | Common bug-prone patterns (e.g. mutable default arguments) | Catches real bugs, not just style |
| `N` | Naming conventions (e.g. classes should be `PascalCase`) | Readability |
| `ANN` | Missing type hints on function signatures | The project's constitution *requires* every function to have type hints — this rule makes that a hard, automatically-checked rule instead of a suggestion someone might forget |
| `T20` | Use of `print()` | The constitution says diagnostic output must use proper logging, not `print()`, except in one-off scripts — this rule enforces that everywhere except a `scripts/` folder |

Also configured: double quotes, spaces (not tabs), Unix-style line endings — a consistent house style.

## Why are `scripts/`, `alembic/`, and `tests/` exempted from some rules?

- **`scripts/`** — one-off utility scripts are allowed to use `print()` (that's literally how you'd
  see output when running them by hand) and don't need the same strict typing as application code.
- **`alembic/`** — this is the folder for auto-generated database migration files; they're mostly
  boilerplate that Alembic itself generates, not hand-written business logic, so requiring full type
  hints there is pointless.
- **`tests/`** — test functions aren't part of the public API anyone calls from outside, so requiring
  type hints on every test function is just busywork; but tests still aren't allowed to use `print()`
  (if a test needs to show you something, that's what assertions and pytest's own output are for).

## What changed in existing code?

Turning the linter on immediately flagged the *existing* `backend/app/reddit/client.py` file (the only
real code in the repo at the time) for two small things:

1. Its imports weren't sorted the way ruff expects.
2. The file didn't end with a newline character (a Unix convention).

Ran `ruff check --fix` and `ruff format`, the auto-fix commands — they rewrote those two cosmetic
things automatically. Verified afterward by re-reading the file: **no logic changed**, only
formatting. This was done so the project starts out passing its own lint check immediately, rather
than being broken from day one by a rule that was just turned on.
