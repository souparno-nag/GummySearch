# T006 — Initialize Alembic with an async migration environment

**Task**: Initialize Alembic in `backend/alembic/` with an async migration environment.

## What problem is this solving?

As the app evolves, the database's structure (tables, columns, indexes) needs to change too — adding
a table for audiences, adding a column for a new feature, and so on. You *could* hand-edit the
database every time, but that doesn't scale past one person or one machine, and there's no record of
what changed or an easy way to undo it. **Alembic** is a migration tool: every schema change is
written as a small Python file (a "migration") that says how to move the database forward (and how to
undo it), and those files live in version control right alongside the code that needs them. The
project's constitution requires *every* schema change to go through Alembic — never hand-editing the
database or using shortcuts like SQLAlchemy's `create_all()` against a real database.

## Why "async" specifically?

The rest of this backend is built on **async** SQLAlchemy — meaning the code that talks to the
database uses Python's `async`/`await` so the web server (FastAPI) can handle other requests while
waiting on a database query, instead of freezing up. Alembic itself doesn't know or care about async
vs. sync by default, so it ships with an alternate project template (`-t async`) that generates a
migration environment already wired for `async`/`await`, so migrations use the same connection style
as the actual application.

## What got created

- **`backend/alembic.ini`** — Alembic's main config file. Says where to find migration scripts
  (`script_location = alembic`) and, ordinarily, the database connection string. We deliberately left
  the connection string **blank** here rather than writing it in — even a placeholder like
  `driver://user:pass@localhost/dbname` sitting in a config file is the kind of thing that's easy to
  accidentally leave as a real credential later. Real credentials only ever live in `.env` at the
  repo root (which is gitignored), per the constitution's rule that secrets are never hardcoded.
- **`backend/alembic/env.py`** — the actual migration runner. This is where the "async" template's
  logic lives: it creates an async database engine and runs migrations through it. Edited to:
  - Load the repo-root `.env` file itself (`load_dotenv(...)`) and read `DATABASE_URL` from it,
    then hand that connection string to Alembic at runtime — so the real password only ever exists
    in the gitignored `.env` file, matching the pattern `backend/app/config.py` will formalize in T007.
  - Leave `target_metadata = None` for now, with a comment explaining it'll later point at the
    shared table registry once actual database models exist (starting around T033).
- **`backend/alembic/script.py.mako`** — the template new migration files get generated from
  whenever someone runs `alembic revision`. Untouched, generated as-is.
- **`backend/alembic/versions/`** — where the actual migration files will land. Still empty — no
  models exist yet, so there's nothing to migrate. The first real migration is T035.

## The awkward part: `alembic init` and an existing directory

Alembic's `init` command refuses to run into a directory that already has files in it — and
`backend/alembic/versions/` already existed (created empty back in T001), which was enough to make it
refuse. Rather than deleting and recreating that folder, `alembic init` was run once into a throwaway
temp directory, and then just the three generated files (`env.py`, `script.py.mako`, `README`) were
copied into the real `backend/alembic/` folder, leaving the existing empty `versions/` alone. The
`alembic.ini` it generated pointed at that temp path, so it needed a one-line fix afterward
(`script_location = alembic`) to point back at the real folder.

## Verification

This wasn't just "the files exist" — it was tested against the actual running database:

```bash
alembic current
```

connected to the live Postgres container (from T005) over the async driver and reported a clean,
empty state — no errors, no migrations applied (correct, since none exist yet). This confirms the
whole chain works: `.env` → `env.py` → async engine → real Postgres connection. `ruff check`/`ruff
format` were also run against the new `env.py` (one import-order issue was auto-fixed, no logic
changed).
