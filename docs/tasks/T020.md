# T020 — Hashed credentials and expiring, invalidatable sessions

**Task**: Implement hashed credential storage, expiring and invalidatable sessions in
`backend/app/users/auth_service.py`.

This is the first file in the `users/` module, and the implementation half of T019's tests.

## What it exposes

| Function | Role |
|---|---|
| `hash_password(password)` | Produce a storable scrypt hash |
| `verify_password(password, encoded)` | Check a password against one |
| `authenticate(username, password)` | Check against the *configured* credential |
| `create_session(redis, username)` | Issue a session, return the token |
| `get_session(redis, token)` | Resolve a token, or `None` |
| `invalidate_session(redis, token)` | Sign out |
| `invalidate_all_sessions(redis)` | Sign out everywhere |

Plus `Session` (a frozen dataclass) and `utc_now()`.

## Credential storage

The encoded form is:

```text
scrypt$16384$8$1$<salt base64>$<hash base64>
```

**Why scrypt from the standard library.** The constitution's Technology and Data Constraints fix the
committed stack and require the amendment procedure for anything outside it. `bcrypt`, `passlib`, and
`argon2-cffi` are all outside. `hashlib.scrypt` is stdlib and is a genuine memory-hard KDF — this is
not a compromise made to dodge paperwork, it is the right tool that also happens to need no
dependency. At `n=16384, r=8` each verification costs roughly 16 MiB of memory, which is what makes
offline guessing expensive.

**Why the parameters are stored in the hash.** Raising the cost later must not lock the user out. With
`n`, `r`, and `p` travelling alongside the salt, an old hash still verifies under its own parameters
while new ones use the new cost.

**Why malformed input returns `False` instead of raising.** `verify_password` catches `ValueError`,
`TypeError`, and `MemoryError` and reports a plain mismatch. A hand-edited or truncated
`AUTH_PASSWORD_HASH` must fail closed as "wrong password". The alternative is a traceback on the
sign-in path that describes exactly how credentials are stored — an error message doing an attacker's
reconnaissance. `MemoryError` is in that list specifically because a *tampered* value could carry an
absurd `n` and try to exhaust memory.

**Comparison is constant-time.** `secrets.compare_digest`, so how long a comparison takes does not
reveal how many leading bytes matched.

## `authenticate` and the empty-hash case

`AUTH_PASSWORD_HASH` defaults to empty, which is the state of a fresh checkout. The dangerous reading
of "no password configured" is "no password required", and that is precisely the class of shortcut
FR-079 forbids. So an empty hash denies everyone and logs why, naming the setting to fix.

Both halves of the check are evaluated before being combined:

```python
username_matches = secrets.compare_digest(username, settings.auth_username)
password_matches = verify_password(password, stored)
return username_matches and password_matches
```

Short-circuiting on the username would make a wrong username return measurably faster than a wrong
password, which tells an attacker when they have guessed the username.

## Sessions

**Only a digest of the token is stored.** The Redis key is `session:<sha256 of token>`, and the token
appears in neither the key nor the value. If a Redis dump or a nightly backup leaks — and FR-070 means
backups exist — what leaks is not a set of usable sessions. Verified directly against the running
container:

```text
stored key     : session:762e9dbab4253c843da1353f1e79c454f0fabe0b67de9625f5d4b4fe845800c3
token in key?  : False
redis ttl      : 43200 seconds
```

SHA-256 rather than a slow KDF is correct here. A slow KDF exists to make guessing a *low-entropy*
secret expensive; these tokens are 32 random bytes from `secrets.token_urlsafe`, so there is nothing
to guess and the only requirement is that the digest is not reversible.

**Expiry is checked twice, on purpose.** Redis carries a TTL matching the session deadline, and
`get_session` independently compares `expires_at` against the current instant. The TTL is what stops
expired sessions accumulating; the explicit check is what decides whether a session authenticates. If
the two ever disagree — an entry that outlived its TTL, a store restored from a dump without expiry
metadata — the safe answer wins. A test simulates exactly that by re-storing an entry with no TTL.

**`Session.__repr__` redacts the token.** Any code path that logs a session — an exception handler, a
debug line — would otherwise write a live credential to disk.

```text
Session(token='<redacted>', username='researcher', created_at=..., expires_at=...)
```

**`invalidate_all_sessions` selects by prefix**, never flushes. Redis also holds the Reddit cache and
(from T022) rate-limit counters. Signing out everywhere must not discard cached listings that cost
Reddit quota to rebuild.

## The judgment call: sessions live only in Redis

The constitution says Redis "MUST be treated as reconstructible from PostgreSQL, so no data may exist
only in Redis". Sessions here do live only in Redis.

The argument that this is consistent rather than a violation: the rule protects the **corpus**. R14 is
explicit that collected material is irreplaceable because Reddit will not serve history beyond its
listing limits — that is what makes "reconstructible" the property worth demanding. A session is the
definition of reconstructible; losing every session costs one sign-in. The alternative, a sessions
table plus a migration, is real schema no task in this phase allocates, protecting data whose loss is
an inconvenience.

It is recorded here rather than left implicit so a reviewer can disagree deliberately. If sessions
ever need to survive a Redis restart, the move to PostgreSQL is a change to four functions in this
file and nothing else.

## What is deliberately not here

No registration endpoint, no roles, no tenancy scoping (R11 — single user; sign-in exists to protect
one person's data, not to separate accounts). No routes at all: `contracts/rest-api.md` is the single
source of truth for the HTTP surface, and the sign-in endpoints are not this task's to invent.
