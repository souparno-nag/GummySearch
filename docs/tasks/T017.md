# T017 — Failing tests for the startup bind guard

**Task**: Write failing tests for the startup bind guard in `backend/tests/unit/test_bind_guard.py`.

## What problem is this solving?

The application is meant to run on one person's machine. FR-078 says binding it anywhere else must
take a deliberate configuration change, and the specification's final edge case is blunt about what
happens otherwise:

> The application is started bound to a non-local interface without the explicit exposure setting —
> it refuses to start and explains why, rather than silently becoming reachable from the network.

"Silently" is the operative word. The failure this guards against is not an attack; it is someone
typing `--host 0.0.0.0` to test something from their phone, forgetting, and leaving a tool holding
Reddit credentials and a database listening on a café network. Nothing about that goes wrong loudly.

This task writes the tests. T018 writes the guard. They are split on purpose, so the test-first step
Constitution IV requires cannot be skipped by writing both at once and declaring the tests passed.

## Why the tests come first, concretely

Test-first is easy to treat as ceremony. Here it does real work: writing these tests forced the guard's
shape to be decided *before* any implementation existed to bias it. Three decisions fell out of writing
them, and all three are visible in the test file:

1. **The guard is pure functions taking arguments**, not something reading global state. That is why
   `assert_bind_allowed(host, *, allow_remote_exposure=...)` takes the flag rather than reading
   settings. A version reading globals would need monkeypatching in every test.
2. **It must read uvicorn's `--host` argument**, not just configuration. This is the one that would
   have been missed. See below.
3. **The refusal message must name the host and the setting.** Asserted directly, because a guard that
   refuses without explaining just moves the confusion.

## The decision worth understanding: where does "the host" come from?

The obvious design is a `APP_HOST` setting the guard checks. It is also nearly useless, because
`quickstart.md` documents starting the server like this:

```bash
uvicorn app.main:app --reload
```

Someone exposing this application does not edit a setting. They type `uvicorn app.main:app --host
0.0.0.0`. A guard reading only configuration would look at `APP_HOST`, see the loopback default, say
"all good", and let uvicorn bind every interface anyway. It would pass its own tests and protect
nothing.

So `resolve_bind_host()` reads the command line first and falls back to configuration. Both paths are
tested, including the `--host=0.0.0.0` joined form and a trailing `--host` with no value after it.

## What the tests cover

**Which hosts are local** — `127.0.0.1`, but also the rest of `127.0.0.0/8` (a `/8` is loopback, not
just the one familiar address), `localhost`, IPv6 `::1`, and the bracketed `[::1]` form uvicorn
accepts. Whitespace and capitalisation must not change the verdict.

**Which are not** — `0.0.0.0` and `::` (every interface), private LAN addresses, public addresses, and
the empty string.

**Unresolvable hostnames are treated as remote.** The guard does not do DNS. Partly because
Constitution IV forbids tests touching the network, but mainly because resolution is not a fact — the
answer can change, and it can be influenced. Failing closed means an unrecognised name is refused
rather than quietly permitted.

**The flag reverses the refusal, and nothing else does.** This is SC-020 in test form: exposing the
application must be a configuration change and *no code change*. If making this test pass ever
required editing source, the requirement would be unmet.

**The guard is actually called.** Three tests build the application with `sys.argv` patched. A guard
nothing calls is decoration, and this is the test that fails if a later refactor drops the call.

## Verifying they fail for the right reason

A test that fails because of a typo proves nothing. Running them gives:

```text
ImportError: cannot import name 'UnsafeBindError' from 'app.main'
```

Which is correct: the guard does not exist yet. That is the state T018 changes.

## The suite is red after this commit, deliberately

Constitution IV requires the full suite to pass before a *change* is complete, and T017 plus T018 are
one change split across two commits so the sequence is auditable. The suite goes green again at T018.
This is the only reason a red commit is acceptable here.
