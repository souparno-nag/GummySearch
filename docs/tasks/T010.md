# T010 — evals/ tree and run_eval.py entry point

**Task**: Create the `evals/` tree with `datasets/`, `results/`, and a `run_eval.py` entry point.

## What problem is this solving?

Later in this project, the AI features (theme tagging, sentiment scoring, "Ask" retrieval) need to be
*measured*, not just built and trusted on sight — the project's constitution requires a labeled
reference set for every AI capability, and requires every prompt/model/retrieval change to be
accompanied by a before-and-after score against that set. `evals/` is where that measurement machinery
lives, kept as a top-level folder separate from `backend/` because — as `plan.md` puts it — it's "a
measurement artifact of the project, not application code."

`datasets/` and `results/` already existed as empty folders from T001 (the very first task, which just
laid out the whole directory tree). This task adds the piece that was still missing: `run_eval.py`,
the actual command someone runs to execute an evaluation.

## Why is `run_eval.py` mostly *not* implemented yet?

This is the interesting part of this task. Looking at the plan, three other tasks are directly
relevant:

- **T079/T080/T100** — label the actual reference data (theme/topic examples, sentiment examples,
  question-to-post relevance examples) into `evals/datasets/*.jsonl`.
- **T081** — build the real scoring logic that reads those datasets and compares the AI model's output
  against them.

Both of those happen much later (Phase 5/6), once the AI services being measured actually exist —
there's nothing to score yet, because nothing produces themes, sentiment, or answers yet. So writing a
"real" scoring harness right now would mean writing code against services that don't exist, which
would just be broken or fake.

Instead, `run_eval.py` was written as an honest **scaffold**: a real, runnable entry point that does
exactly one useful thing today — check whether the required dataset files exist, and say clearly what
state things are in, rather than either crashing with a confusing error or silently pretending to
succeed. This matters because `quickstart.md` documents `python evals/run_eval.py` as a command that
must be run before any prompt/model/retrieval change ships; having it exist and behave sensibly from
day one (even before it does real scoring) means nothing later has to remember to create it from
scratch.

## What it actually does right now

Two states, both verified by actually running the script:

1. **No dataset files yet** (the current state of the repo) — logs an informational message naming
   exactly which files are missing and which tasks will create them, and exits with status `0`
   (success — this is the expected, unremarkable state, not an error).
2. **Dataset files exist, but the scoring logic doesn't** — logs an error saying so, and exits with
   status `1` (failure — if someone eventually adds the datasets before T081 lands, running this
   should fail loudly rather than silently doing nothing).

Both branches were tested directly: ran it against the real (empty) `datasets/` folder to confirm the
first message and exit code, then created three empty placeholder files to trigger the second branch,
confirmed *that* message and exit code, and deleted the placeholders again immediately afterward —
they were only ever temporary, to prove the logic branches correctly, not real data.
