# T011 — Async engine and session factory (`common/database.py`)

**Task**: Implement the async engine and session factory in `backend/app/common/database.py`.

## What problem is this solving?

The application stores everything it collects — posts, comments, audiences, alert rules — in
PostgreSQL. Before any of that can be written or read, the app needs three things that every later
module will share:

1. A **connection to the database** it can reuse, rather than opening a fresh one per query.
2. A **session** — the object you actually run queries through, and which groups a set of changes
   into one transaction that either all lands or all gets undone.
3. A **declarative base** — the common parent class that ORM models inherit from, which is how
   SQLAlchemy learns what tables exist.

T011 builds all three in one place so no module ever has to invent its own.

## Why one shared engine?

An *engine* in SQLAlchemy is not a connection; it is a **pool** of connections plus the knowledge of
how to talk to this particular database. Opening a TCP connection to PostgreSQL and authenticating
takes real time (tens of milliseconds), which is unacceptable to pay on every request. The pool keeps
a handful of connections open and hands one out when asked, returning it afterwards.

That only works if there is **one** pool. If each of the six modules built its own engine, the process
would hold six separate pools, each with its own idle connections, and PostgreSQL's connection limit
would be consumed six times faster than anyone expected. So the engine is created exactly once, here,
and everything else imports it.

Creating the engine does **not** connect to anything. SQLAlchemy opens the first real connection
lazily, on first use, so importing this module never performs I/O — which matters because the module
gets imported at startup, by tests, and by Alembic.

## Why *async*?

The project's constitution forbids blocking I/O on request paths. A normal ("synchronous") database
driver stops the entire thread while it waits for PostgreSQL to answer — during which the server can
serve nobody else. An async driver hands control back to the event loop while waiting, so other
requests keep moving. That is why the connection string starts with `postgresql+asyncpg://`:
`asyncpg` is the async PostgreSQL driver, and `create_async_engine` (rather than `create_engine`) is
its SQLAlchemy counterpart. There is a test asserting this specific driver, because switching to a
synchronous one would quietly reintroduce blocking without any obvious symptom until load arrives.

## What's actually in the file

### `Base` — the shared declarative base

Every ORM model in every module will inherit from this class. All of them registering on one shared
`MetaData` object is what lets Alembic's autogenerate see the *whole* schema in one pass and produce
a single correct migration. (`backend/alembic/env.py` already has a commented-out
`from app.common.database import Base` waiting for the first models to land in T033.)

This does not weaken the module boundary rule in the constitution. That rule is about which module may
**query** which tables — it is not about which metadata object the tables are registered on.

### The naming convention

`Base.metadata` is configured with a `naming_convention` — templates that decide what primary keys,
foreign keys, indexes, and unique constraints are *called* in the database.

This looks like a pedantic detail and is not. If you don't name a constraint, PostgreSQL invents a
name for it. Months later, a migration that needs to remove that constraint has to refer to it by
name — and the generated name may differ between machines, or be something Alembic cannot guess.
The result is a migration that works on one database and fails on another. Fixing this **before the
first table exists** costs nothing; fixing it afterwards means renaming every constraint already in
production. Hence: every constraint this project ever creates is named predictably, starting now.

### `engine` — the connection pool

Configured with a modest pool (5 connections, up to 10 more under burst — correct for a single-user
tool) and two settings worth explaining:

- **`pool_pre_ping=True`** sends a trivial "are you alive?" query before handing out a pooled
  connection. Without it, a connection the server has quietly dropped — because the Docker container
  restarted, or an idle timeout fired — gets handed to a request, which then fails with a confusing
  error. With it, SQLAlchemy notices the dead connection and transparently opens a new one.
- **`pool_recycle=1800`** retires connections after 30 minutes, so the pool never accumulates
  very old connections that intermediaries may be about to sever anyway.

### `session_factory` — where sessions come from

An `async_sessionmaker` — essentially a configured factory that produces sessions on demand. Two
non-default settings:

- **`expire_on_commit=False`**. By default, SQLAlchemy marks every object as "stale" after a commit,
  so the next attribute read re-fetches it from the database. In async code that behaviour is worse
  than slow: the implicit refresh **raises an error** rather than silently issuing a query. Turning it
  off means an object you just saved stays readable, which is exactly what a route needs when it
  returns the thing it just created.
- **`autoflush=False`** stops SQLAlchemy from sending pending changes to the database at unpredictable
  moments (before an unrelated query, for instance). Writes go out when the code says so.

### `get_session()` — the per-request session

This is the function FastAPI routes will depend on, and it owns the **transaction boundary**:

```python
async with session_factory() as session:
    try:
        yield session
        await session.commit()      # the request succeeded — make the changes permanent
    except Exception:
        await session.rollback()    # something failed — undo everything
        raise
```

The `yield` in the middle is what makes this a FastAPI dependency: the route runs while the function
is paused at the `yield`, and the code after it runs once the route finishes.

Putting commit and rollback *here* rather than inside each service function is the important design
choice. If every service committed its own work, a request that called three services and failed on
the third would leave the first two permanently written — a half-finished operation with no record
that anything went wrong. With one boundary per request, the request either lands completely or not
at all.

Note that the exception is **re-raised**, not swallowed. Rolling back is this function's job;
deciding what the user sees is the error-envelope middleware's job (T014).

### `dispose_engine()`

Closes every pooled connection. Called when the app shuts down, and by any script or worker that is
finished with the database, so the process doesn't exit while still holding connections open on the
server side.

## Tests

`backend/tests/unit/test_database.py` — seven tests, none of which open a connection. The constitution
forbids tests contacting external systems, and everything here is either configuration decided at
import time or transaction behaviour that can be checked against a stand-in session object:

- the engine uses the async driver, and pre-pings pooled connections
- committed objects stay readable (`expire_on_commit=False`)
- constraints are named deterministically
- a successful request commits exactly once and closes the session
- a failing request rolls back, does **not** commit, and lets the exception propagate
- disposing the engine releases its connections

Coverage of `app/common/database.py` is 100%.

## One change outside the task's file

`backend/pyproject.toml` gained `pythonpath = ["."]` under `[tool.pytest.ini_options]`. Without it,
pytest cannot `import app.common.database` from a test file — Python simply doesn't know where `app`
lives. This is the standard fix and is preferable to the alternative (a `conftest.py` that edits
`sys.path` by hand). It was needed now only because T011 is the first task to have a test that
imports application code.

## A snag worth recording (resolved): port 5432 was not the container

The intent was to finish by connecting to the real database, as every task so far has been verified
against real infrastructure. That failed with `password authentication failed for user "jammysearch"`.

The cause is the one the T005 notes warned about: a **native PostgreSQL 16 service** is running on
this machine and holds `0.0.0.0:5432`. The `docker-compose.yml` container asks for `127.0.0.1:5432`,
cannot get it, and ends up running with **no published port at all** (`docker compose ps` shows a bare
`5432/tcp` rather than a mapping) while still reporting healthy. So `localhost:5432` reaches the
native PostgreSQL — which has no `jammysearch` role — and the failure looks like a wrong password
rather than the wrong server.

Connecting straight to the container's bridge IP instead is not a workaround here: under Docker
Desktop the containers live inside a VM, so those addresses are not routable from the host.

The fix was to free port 5432 by retiring the native cluster, leaving `docker-compose.yml` and `.env`
exactly as committed and keeping 5432 as the conventional port:

```bash
sudo systemctl disable --now postgresql@16-main
sudo systemctl stop postgresql.service
docker compose up -d --force-recreate postgres
```

The `--force-recreate` matters: the container had already started without its port mapping, and
merely restarting it would not have re-attempted the bind. Afterwards `docker compose ps` shows the
real mapping, `127.0.0.1:5432->5432/tcp`, instead of a bare `5432/tcp`.

The live check then passed — connecting through `get_session()` to PostgreSQL 16.15 as
`jammysearch/jammysearch`, returning a healthy pool afterwards and disposing cleanly. That the
database and role are both `jammysearch` is what proves it is the project's own pgvector container
and not the native cluster, which never had that role — the very mismatch that produced the
misleading password error.

**If this recurs**, the diagnostic that identifies it immediately is `docker compose ps`: a service
showing a bare `container-port/tcp` with no `host:port->` arrow is a container whose publish failed,
not a container that is down.
