# T004 — Configure pytest, pytest-asyncio, and the coverage gate

**Task**: Configure pytest, pytest-asyncio, and a hard-failing 80% service-layer coverage gate in
`backend/pyproject.toml` so every run enforces Constitution IV rather than deferring it.

## What problem is this solving?

Tests prove the code does what it's supposed to. But "we have some tests" isn't the same guarantee as
"the important logic is actually tested" — it's easy to end up with tests for the easy stuff and none
for the tricky business logic (search filtering, deduplication, alert matching) where bugs actually
hide. The project's constitution sets a rule: the "service layer" — the code that does the real
decision-making — must have at least 80% of its lines exercised by tests, and a change that drops
below that floor is considered incomplete, full stop.

This task wires up the tools that make that rule *automatic* rather than something someone has to
remember to check.

## What are these tools?

- **pytest** — the test runner. You write functions like `def test_something(): assert ...` and
  pytest finds and runs them, reporting pass/fail.
- **pytest-asyncio** — a plugin that lets pytest run `async def` test functions. This project uses
  async database access and async API endpoints (per the constitution's "no blocking I/O" rule), so
  tests need to be able to `await` things too.
- **pytest-cov** — a plugin that measures *coverage*: while your tests run, it watches which lines of
  your actual application code actually got executed, and reports a percentage. It's built on top of
  a lower-level library called `coverage`.

## What was configured, and why

In `backend/pyproject.toml`:

- **`testpaths = ["tests"]`** — tells pytest where to look for test files, so it doesn't go
  wandering through the whole repo.
- **`asyncio_mode = "auto"`** — lets test functions be written as plain `async def test_...():`
  without needing to remember an extra decorator on every single one.
- **`addopts = "--cov=app --cov-report=term-missing --cov-fail-under=80 --strict-markers"`** — this
  is the important line. Every time you just type `pytest`, it automatically:
  - measures coverage of the `app/` folder (`--cov=app`),
  - prints exactly which lines were *not* covered so you know what to test next
    (`--cov-report=term-missing`),
  - and **fails the whole run** if coverage drops below 80% (`--cov-fail-under=80`) — this is the
    "hard-failing gate" the task asks for. It's not a report you can ignore; a low-coverage run exits
    with a non-zero status, the same way a failing test would.
  - `--strict-markers` makes pytest error out if a test uses a marker (a tag like `@pytest.mark.slow`)
    that was never registered, which catches typos in test tags early.
- **`[tool.coverage.run]`** — tells the coverage tool to only look at the `app/` source folder, to
  count both straight-line and branching coverage (`branch = true`, i.e. it checks that both sides of
  an `if` were actually exercised, not just that the line ran), and to skip
  `app/ai/prompts/*` — those are versioned prompt *text* files, not executable logic, so "coverage"
  doesn't mean anything for them.
- **`[tool.coverage.report]`** — repeats the 80% floor at the reporting level too (belt and braces),
  and tells the tool to ignore a few lines that are impossible or pointless to test, like
  `raise NotImplementedError` placeholders.

## Why configure this now, when there's almost no code yet?

This is deliberate, and called out explicitly in the project's own handoff notes: the coverage gate
must be enforcing *from the very first test*, not bolted on later once a habit of skipping tests has
already formed. Configuring it in T004 — right after the project skeleton exists, before any real
service logic is written — means every single task after this one is written against a gate that's
already live, rather than everyone hoping to "add tests later."
