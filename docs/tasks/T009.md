# T009 — Initialize the SvelteKit application

**Task**: Initialize the SvelteKit application (adapter-static, SSR off — R10) in `frontend/`.

## What problem is this solving?

Everything so far has been backend (Python/FastAPI/Postgres). This task starts the other half: the
web page you'll actually look at in a browser. Rather than hand-writing an HTML/JS project from
scratch, **SvelteKit** ships an official scaffolding tool (`sv create`) that generates a working
starting project — build tooling, TypeScript setup, folder conventions — already wired together
correctly, the same way `alembic init` did for migrations in T006.

## Vite — is it in use?

Yes. This came up as a direct question: SvelteKit is a *framework* built on top of **Vite**, which is
the actual dev server and bundler doing the work underneath (compiling code, serving pages during
development, producing the final optimized files for production). Choosing SvelteKit means Vite comes
along automatically — there was never a separate "use Vite or not" choice once SvelteKit was picked;
the earlier "plain Vite + Svelte" alternative discussed and set aside just meant using Vite directly
*without* SvelteKit's extra framework layer (routing, SSR, etc.) on top of it.

## What "SSR off" and "adapter-static" mean, and why they needed extra configuration

By default, SvelteKit is built to run on a server that renders each page's HTML on the fly per request
(**server-side rendering**, SSR) — useful for many apps, but pointless here since this project's
*actual* server is the separate FastAPI backend; the frontend's only job is to call that backend's API
and render the result in the browser. So SSR needed to be turned off, and the app needed to be built as
a set of static files an ordinary web server (or even just opening the file) can serve — that's what
the `adapter-static` add-on and `sv create`'s `--add sveltekit-adapter="adapter:static"` flag set up.

There was one extra wrinkle the base scaffold didn't handle automatically: pages like
`/audiences/[id]/feed` have a piece of their URL (`[id]`) that's only known at runtime — a real
audience someone created — not at build time, when the static files are generated once and for all.
A purely static site can't pre-generate a page for every possible audience ID that will ever exist.
The fix is **SPA fallback mode**: configure the adapter with `fallback: 'index.html'`, so any URL that
doesn't match a pre-built page is served the same base HTML shell, and the page's own client-side
JavaScript figures out from the URL which audience to load and fetches its data from the API. This
also required explicitly disabling SSR in the root layout (`export const ssr = false` in
`src/routes/+layout.ts`) — a fallback page has no server to render on, so SvelteKit needs to be told
upfront not to try. Both of these were added by hand after scaffolding, since the CLI's defaults
assume a fully pre-renderable site.

## What got scaffolded

Ran `sv create` (the official SvelteKit CLI) with these choices, matching decisions already recorded
in `research.md` (R10) and `plan.md`:

- **TypeScript** — matches `plan.md`'s "TypeScript (frontend)".
- **ESLint + Prettier** — the frontend's equivalent of the backend's `ruff`: one catches bugs and
  style issues (ESLint), the other enforces consistent formatting (Prettier).
- **Vitest** — the frontend's equivalent of the backend's `pytest`: a test runner for component and
  unit tests.
- **adapter-static**, configured for SPA fallback as described above.

Scaffolding was done into a throwaway temp directory first (same workaround used for Alembic in T006)
because `sv create` refuses to run into a non-empty folder, and `frontend/src/{design,components,
routes,services}/` already existed from T001. Only the generated files were then copied in —
`design/`, `components/`, and `services/` (the project's own planned structure) were left untouched.
`frontend/src/pages/` was renamed to `frontend/src/routes/` first, matching SvelteKit's own routing
convention (a file at `routes/audiences/[id]/feed/+page.svelte` becomes the URL
`/audiences/:id/feed` — no separate router library needed, the folder structure *is* the routing
table).

## Verification

Every step was actually run and checked, not just assumed to work from the generated files:

- `npm run build` — succeeded, produced a real `build/` folder including `index.html` (serving as
  both the homepage and the SPA fallback page).
- `npm run lint` — Prettier and ESLint both pass clean.
- `npm run test` — the scaffold's example test passes.
- `npm run dev` — started the real development server, and a `curl` request to
  `http://localhost:5173/` came back `HTTP 200`, confirming it actually serves pages, not just starts
  without crashing. It was bound to `localhost` only, by default — no `--host` flag — matching the
  project's local-first posture.
- Confirmed with `git status`/`git check-ignore` that `node_modules/`, `.svelte-kit/` (SvelteKit's
  generated build cache), and `build/` are all excluded from git by the scaffold's own generated
  `frontend/.gitignore`, so none of that gets committed.

One cosmetic fix: the scaffold names the package after the temp directory it was generated in
(`sveltekit-tmp`); renamed to `jammysearch-frontend` in `package.json` after copying in.

`npm audit` reports 3 low-severity issues in a transitive dev-tooling dependency (`cookie`, pulled in
by SvelteKit's own tooling, not by anything this project's code touches directly). The suggested
"fix" would force-downgrade `@sveltejs/kit` to a pre-1.0 version — clearly wrong, not a real fix — so
it was left alone rather than applying a destructive downgrade for a low-severity, non-exploitable
issue in a locally-run tool.
