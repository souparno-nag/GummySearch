# T013 — Typed exception classes (`common/exceptions.py`)

**Task**: Define typed exception classes in `backend/app/common/exceptions.py`.

## What problem is this solving?

Things go wrong constantly in a web application: a requested audience doesn't exist, Reddit stops
responding, a limit is hit. Each of those needs to reach the user as a clear explanation and the right
HTTP status code — 404 for "not there", 502 for "someone else's server broke" — and they need to do so
*consistently*, so the frontend can handle them uniformly.

The naive approach is for each route to notice the problem and build its own error response. That
fails in three ways: the shape drifts between routes, the HTTP status for the same kind of problem
ends up different in different places, and sooner or later a raw Python exception message leaks to the
user (`KeyError: 'subreddit_id'` tells an attacker about your internals and tells a researcher
nothing).

The fix is to split the job in two. **This task** defines the vocabulary of failures. **T014** defines
the single place that turns them into HTTP responses.

## Exceptions as a vocabulary

`AppError` is the base class; everything else inherits from it. Each carries three things:

- **`status_code`** — the HTTP status, fixed *on the class* rather than chosen wherever it's raised.
  This is the point: if `NotFoundError` is 404 by definition, no route can accidentally answer 400 for
  a missing audience while another answers 404 for the same thing.
- **`code`** — a short, stable, machine-readable string like `not_found` or `audience_limit_reached`.
  The frontend branches on this. It's separate from the message because the message is prose meant for
  a human and may be reworded at any time; the code is an identifier and must not change casually.
- **`message`** — the sentence a user actually reads. FR-052 requires it state *what failed and what
  to do next*, which is why every class ships a usable default rather than depending on the raise site
  to write one.

There's also **`details`** — an optional dict for structured context (which field was invalid, which
community was unavailable). It defaults to `{}` rather than `None` so the envelope can always render
it without a guard. It must never carry internal state, credentials, or a traceback.

## The classes, and why these ones

| Class | Status | When |
|---|---|---|
| `AppError` | 500 | Base class; also the fallback for genuine bugs |
| `ValidationError` | 422 | Request was well-formed but its contents aren't acceptable |
| `NotFoundError` | 404 | Doesn't exist, or isn't this user's to see |
| `ConflictError` | 409 | Valid request, conflicts with current state (limits, duplicates) |
| `AuthenticationError` | 401 | Nobody is signed in |
| `AuthorizationError` | 403 | Signed in, but not allowed to touch this |
| `RateLimitedError` | 429 | Too many requests (FR-080) |
| `SpendCeilingError` | 429 | A configured spend ceiling is exhausted (FR-046) |
| `UpstreamError` | 502 | Reddit or the model provider failed |
| `DegradedError` | 503 | A capability is currently unavailable (FR-049) |

Three of these distinctions are load-bearing and worth spelling out, because collapsing any of them
would quietly break a measurement the project depends on:

**`RateLimitedError` vs `SpendCeilingError`.** Both answer 429. They are separate classes because
*waiting fixes only one of them*. A rate limit clears in seconds. An exhausted spend ceiling does not —
it resets on its own schedule or has to be raised in configuration. Telling a user "wait a moment and
try again" when the real answer is "you've used this period's budget" is an unhelpful error, which is
exactly what FR-052 prohibits.

**`UpstreamError` vs `AppError`.** A provider outage is not an application bug and must never be
reported as a 500. Beyond honesty, this matters for the Ask feature: the constitution requires
`refused` (the system correctly declining to answer from thin material) and `failed` (the provider
breaking) to stay distinct, because conflating them corrupts the SC-007 refusal measurement by
counting outages as correct refusals. That separation starts here, in the type system.

**`AuthenticationError` vs `AuthorizationError`.** 401 means "we don't know who you are — sign in";
403 means "we know who you are and the answer is no". Different statuses, different user actions.

## What is deliberately *not* here

No domain-specific classes — no `AudienceNotFoundError`, no `SubredditBannedError`. The modules that
own those concepts pass their own `code` to the general class instead:

```python
raise ConflictError(
    "This audience already has 50 communities. Remove one before adding another.",
    code="audience_limit_reached",
)
```

That's the exact error from the API contract's example envelope. Doing it this way keeps `common/`
free of knowledge about audiences and alerts — which is the constitution's rule that shared helpers
live in `app/common/` only when genuinely shared, not because one module needed them first.

The `code` is set on the *instance*, not the class, so a specific raise never changes the default for
every later use of the same type. There's a test pinning that, because it's the kind of thing that
would work fine until the day it didn't.

## Tests

`backend/tests/unit/test_exceptions.py` — twelve tests, most parametrized across every class so that a
class added later is automatically held to the same contract:

- every error is catchable as `AppError` (the handlers in T014 register against the base class alone,
  so anything outside the hierarchy would be reported as an unexpected 500)
- every error carries a status, a lowercase code, and a usable default message
- `str(error)` returns the user-facing sentence, so logs and formatting don't print a bare class name
- a raise site can supply its own code and message, and doing so doesn't leak into other instances
- `details` defaults to `{}` and carries structured context
- each status matches its meaning
- an exhausted ceiling is distinguishable from a rate limit
- an upstream outage is not reported as an application bug

Coverage of `app/common/exceptions.py` is 100%.
