# T014 — Error-envelope handlers (`common/middleware.py`)

**Task**: Implement error-envelope middleware translating typed exceptions to the shared error shape
in `backend/app/common/middleware.py`.

## What problem is this solving?

T013 gave the application a vocabulary of failures. This task builds the single place that turns any
of them into an actual HTTP response — and, just as importantly, catches everything that *isn't* one
of them so no failure escapes in the wrong shape.

The API contract fixes one shape for every error the API can produce:

```json
{
  "error": {
    "code": "audience_limit_reached",
    "message": "This audience already has 50 communities. Remove one before adding another.",
    "details": {}
  }
}
```

A client that handles that shape once handles every error from every endpoint. That only holds if
**nothing** slips out in a different shape — which is why this task is about coverage of failure
sources, not just formatting.

## The four sources of failure

If any of these were left out, it would fall through to Starlette's default handling and answer with
plain text instead of the envelope:

1. **`AppError` and its subclasses** — this project's own typed exceptions. Reported with the status,
   code, message, and details the exception carries.
2. **`RequestValidationError`** — FastAPI rejecting a malformed request *before the route function
   ever runs*. Easy to forget precisely because no application code is involved.
3. **`HTTPException`** — raised by Starlette itself and by FastAPI's own machinery: a 404 for a path
   with no route, a 405 for the wrong method.
4. **Everything else** — a genuine bug. `KeyError`, `AttributeError`, a driver blowing up.

## Why exception handlers rather than middleware

The task named the file `middleware.py`, but the mechanism used is FastAPI's **exception handlers**,
and the difference is worth recording.

Middleware wraps the request from the outside: the request goes in, the response comes out, and
middleware sees exceptions that propagate all the way out of the stack. The problem is that FastAPI
handles `RequestValidationError` *internally* — it never propagates out to middleware, so middleware
cannot reshape it. Registering handlers instead is what makes all four cases reachable from one place.

The file keeps its contracted name; `install_error_handling(app)` is the entry point that T016 calls.

## What each handler does

**`handle_app_error`** — reads the status, code, message, and details off the exception and returns
them. Logs at *warning* level with no traceback: a typed error is the system working as designed, not
a bug, and logging it as an error would train you to ignore real ones.

**`handle_validation_error`** — reshapes FastAPI's validation failure. This one does real work rather
than passing the default through, because FastAPI's default body looks like:

```json
{"detail": [{"loc": ["body", "page_size"], "msg": "...", "input": "not a number", "url": "..."}]}
```

That exposes the internal location tuple and the shape of the Pydantic models behind the endpoint.
The envelope echoes back only the field name and the reason — enough to fix the request, nothing about
the models. Two tests pin this: one that the field is named, one asserting `loc` and `body` do not
appear anywhere in the response text.

**`handle_http_exception`** — wraps framework-raised errors. Since Starlette raises these with a
status but no application `code`, a small lookup table maps the statuses it actually uses onto codes,
so a 404 from an unrouted path is indistinguishable in shape from a 404 raised by application code.
Unmapped statuses fall back to `request_failed` rather than failing. Starlette's `detail` here is its
own wording ("Not Found"), never application internals, so surfacing it is safe.

**`handle_unexpected_error`** — the catch-all. This is the one with a security obligation:

- The client gets a **generic** message and the code `internal_error`. Constitution V forbids raw
  exception text reaching a client, and exception text is exactly where connection strings, file
  paths, and internal identifiers show up.
- The server gets the **full traceback** via `logger.exception`. Hiding it from the user must not mean
  losing it.

Two tests protect the pair. One raises `RuntimeError("asyncpg connection string user=jammysearch
password=hunter2")` and asserts that neither `password`, `asyncpg`, nor `Traceback` appears in the
response. The other asserts `hunter2` *does* appear in the captured logs. That's the whole design in
two assertions: invisible to the client, visible to the operator.

If this handler ever fires in practice, the fix is usually a new typed exception in `exceptions.py`,
not a special case here.

## Tests

`backend/tests/unit/test_error_envelope.py` — twelve tests, each driving a **throwaway FastAPI app**
built in a fixture rather than the real application. That keeps them independent of which routers
happen to be registered, so they won't start failing when T016 and later tasks add routes. Nothing
touches the network; `TestClient` calls the ASGI app in-process.

One detail worth knowing if you write more of these: the client is constructed with
`raise_server_exceptions=False`. By default `TestClient` re-raises server-side exceptions so you see
the real traceback in your test output — which would defeat the tests that check the 500 *response*.

Covered: typed errors keep their status and code; a raise-site code and details reach the client
(asserting the contract's own example envelope); an upstream outage answers 502 rather than 500; an
unexpected bug becomes a generic 500, leaks nothing, and is logged with its traceback; a malformed
request names the field to fix without exposing model internals; unrouted paths and wrong methods use
the same envelope; an unmapped status still produces one; and a framework error with no detail falls
back to the generic message.

Every test also asserts the envelope is the *whole* body — a stray sibling key would break the client
contract just as surely as a wrong shape.

Coverage of `app/common/middleware.py` is 100%.

## Dependency change

`requirements.txt` gained `httpx`, under Testing. `fastapi.testclient` needs it to drive the ASGI app,
and T014 is the first task with a test that makes HTTP calls. Same reasoning as the `redis` line in
T012: it was already installed transitively, but now something in this project imports code that
requires it, so it is declared.

There is a deprecation warning from Starlette suggesting `httpx2` instead. Left alone deliberately —
the current combination works, and chasing it would mean changing a test dependency for no behavioural
gain. Worth revisiting if the warning becomes an error on a future upgrade.
