# T021 — The `current_user` dependency

**Task**: Implement the `current_user` dependency in `backend/app/dependencies.py`.

## What this is

FastAPI's dependency system lets a route declare what it needs and have the framework supply it. This
file adds the one every authenticated route will declare:

```python
@router.get("/audiences")
async def list_audiences(user: CurrentUser) -> Page[AudienceOut]:
    ...
```

Writing `user: CurrentUser` is the whole of it. Before the route body runs, the session cookie is
read, the session is looked up and checked for expiry, and either an `AuthenticatedUser` arrives or
the request is refused with a 401 in the shared envelope.

FR-048 requires sign-in and requires one user's audiences, bookmarks, and notes to stay private. This
is where "is anybody signed in" gets decided — once, centrally, so no router repeats the check and,
more importantly, so none of them can quietly omit it.

## Why a cookie rather than an `Authorization` header

The client is a browser SPA (R10). A cookie can be marked `HttpOnly`, which puts the token out of
reach of any JavaScript on the page — including anything injected. A bearer token in a header has to
be stored somewhere the page's own code can read, which means script that gets onto the page can read
it too.

FR-079 requires secrets never to appear in "anything the client can read", and an `HttpOnly` cookie is
how that is satisfied while still letting the browser authenticate every request automatically.

## Every refusal looks the same

Missing cookie, unknown token, expired session, invalidated session — all produce the same 401. The
only difference is the message for "no cookie at all" ("Sign in to continue.") versus everything else
("Your session has expired. Sign in again to continue.").

That flattening is intentional. Distinguishing "that token never existed" from "that token expired"
tells an unauthenticated caller which tokens were once real, which is information they should not be
able to collect. A test asserts the message does not mention Redis, cookies, tokens, scrypt, or
hashing — a 401 should say what to do next (FR-052), not narrate the authentication scheme.

## `AuthenticatedUser` is a deliberate seam

```python
@dataclass(frozen=True)
class AuthenticatedUser:
    username: str
    session: Session
```

Returning the raw `Session` would have worked today. This deployment is single-user with the
credential in configuration (R11), so there is no `User` row to load and the session already carries
everything anyone needs.

The wrapper exists because that changes. When bookmarks land (T137) there is a persisted user with an
id that foreign keys point at, and something has to load it. When that happens, this is the single
place that changes — every route written as `user: CurrentUser` keeps working untouched. One small
dataclass now avoids editing every router later.

## Tested through a real request

`tasks.md` allocates no test task for T021, and Constitution IV would let this pass as "thin glue".
It is tested anyway, for two reasons: it is a security control, and the failure mode is specifically
one of wiring. A dependency that works when called directly but is not attached to the cookie the
client actually sends protects nothing and would still pass a unit test of the function.

So the tests build a small app with one protected route and drive it through `TestClient` with real
cookies. They cover the refusals, the success, and two properties that would otherwise rot: that an
**expired** session is refused (the test that fails if the dependency ever degrades into "a cookie
exists"), and that an **invalidated** session stops working on the very next request rather than when
its TTL lapses.

Redis is the fake from `conftest.py`, injected with `dependency_overrides`.

## A gap in the contract, noted not filled

There is currently **no way to sign in over HTTP.** `contracts/rest-api.md` states that all endpoints
require an authenticated session and that there is no registration endpoint, but it contracts no
endpoint for *creating* a session either — no `POST /auth/session` or equivalent.

So this dependency can refuse requests and admit sessions, but nothing can issue one except calling
`create_session` directly. That is a real gap, and it is left open on purpose: Constitution III makes
`contracts/rest-api.md` the single source of truth for the HTTP surface and forbids adding an endpoint
it does not describe. Inventing a sign-in route here would be exactly the drift that rule prevents.

The fix is to add the endpoint to the contract first, in its own change set. Flagged here so it is a
recorded decision rather than something discovered when the first protected route ships.
