# T015 — Pagination envelope and page-size ceiling (`common/pagination.py`)

**Task**: Implement the shared pagination envelope and max page size in
`backend/app/common/pagination.py`.

## What problem is this solving?

Most of this application returns *lists*: posts in a feed, search results, alert matches, communities.
None of them can safely return everything they have. An audience that has been collecting for a month
holds tens of thousands of posts, and sending all of them in one response would exhaust memory on the
server, take forever over the wire, and be useless to a UI that shows twenty at a time.

So collections come back one **page** at a time. Two things need deciding once, centrally:

1. **What a page looks like** — so every endpoint answers in the same shape and the frontend writes
   the "load more" logic once instead of eleven times.
2. **How large a page may be** — the ceiling.

## The envelope

Fixed by `contracts/rest-api.md`:

```json
{"items": [], "page": 1, "page_size": 25, "total": 0, "has_more": false}
```

- **`items`** — the rows for this page.
- **`page`** / **`page_size`** — what was asked for, echoed back, so a client holding a response has
  everything it needs to request the next page without tracking state separately.
- **`total`** — how many rows match the query *in total*, not how many are in `items`. This is what
  lets the UI say "showing 25 of 812".
- **`has_more`** — whether another page exists.

`has_more` is redundant in principle (a client could compute it from `page`, `page_size`, and `total`)
and included on purpose. That arithmetic is an off-by-one waiting to happen, and it would be
reimplemented at every call site. Computing it once, server-side, is the whole point.

## The ceiling, and why it rejects rather than clamps

`MAX_PAGE_SIZE = 100`, with `DEFAULT_PAGE_SIZE = 25`. Constitution VI prohibits unbounded queries, and
the reason is worth being precise about: the request is the *caller's* to shape. A frontend that
politely asks for 25 proves nothing, because anyone can send `?page_size=1000000` by hand. If the
ceiling isn't enforced on the server, it isn't enforced.

The less obvious decision is what to do when someone exceeds it. Two options:

- **Clamp** — silently return 100 rows to a request for 1000.
- **Reject** — answer 422 and say why.

This implements **reject**. Clamping produces a response that quietly disagrees with itself: the
caller asked for 1000, got 100, and `total` says 812, so it looks as though rows are missing. The
caller has no way to tell a clamp from an empty result. Rejecting makes the limit visible to the one
person who needs to know it exists — whoever is writing the client.

Because `PageParams` is a Pydantic model used as a FastAPI dependency, the ceiling is enforced by
*validation*, before the route function runs. No service has to remember to check. And since T014
reshapes `RequestValidationError`, the rejection comes back in the shared error envelope naming
`page_size` as the field to fix — the two tasks compose without either knowing about the other.

## `PageParams`

Carries `page` (1-indexed, minimum 1) and `page_size` (1 to `MAX_PAGE_SIZE`), plus two derived
properties for the query layer:

- **`limit`** — rows to fetch; the same as `page_size`.
- **`offset`** — rows to skip, `(page - 1) * page_size`.

The `- 1` is why `offset` lives here rather than at each call site. Pages are 1-indexed because that's
what a human reads ("page 1" is the first page); SQL offsets are 0-based. Getting that conversion
wrong in one service and right in another produces a feed that silently skips or repeats a row, which
is the sort of bug nobody notices for weeks. Page 0 is rejected outright, since it would produce a
negative offset.

## `Page`

A **generic** Pydantic model — `Page[AudienceRead]`, `Page[PostRead]`. The parameterization isn't
decoration: it makes the item type part of the response schema, so the generated OpenAPI document
describes each endpoint's rows precisely instead of calling every collection "a list of anything".
There's a test asserting `Page[int]` really does declare integer items.

Two constructors:

- **`create(items, total, params)`** — the normal path, computing `has_more` as
  `offset + len(items) < total`.
- **`empty(params)`** — a page with nothing in it. Worth having explicitly because an empty result is
  a valid, expected outcome, not an error. Constitution V requires every view to have a designed
  *empty* state, and a route that returned 404 for "no matches" would deny the UI the ability to
  render it.

## Tests

`backend/tests/unit/test_pagination.py` — sixteen tests, all pure computation except the last:

- defaults put the first page at offset 0, and the offset follows the 1-indexed page
- a page size above the ceiling is rejected; the ceiling itself is allowed
- page 0 and negative pages are rejected; a page size of 0 is rejected
- `has_more` is right for a full first page, a short last page, an exactly-full last page, a single
  short page, and a page past the end
- an empty result is a page, not an error
- the envelope has exactly the contracted keys — an extra or missing one breaks every client at once
- the item type is carried into the generated schema
- the ceiling is enforced **over HTTP**, returning the shared error envelope with `page_size` named

That "exactly full final page" case is the one worth keeping: 50 rows at 25 per page ends precisely on
page 2, and a naive `has_more` implementation cheerfully advertises a page 3 that doesn't exist.

Coverage of `app/common/pagination.py` is 100%.

## A convention set here: `Annotated` over `Depends()` defaults

The HTTP test originally declared its dependency the older way:

```python
async def items(params: PageParams = Depends()):
```

`ruff` rejected it (B008 — no function calls in argument defaults, since a default is evaluated once
at import and shared). FastAPI is a special case where that pattern is safe, but rather than silence
the rule, the code uses the modern form FastAPI itself now recommends:

```python
async def items(params: Annotated[PageParams, Depends()]):
```

Identical behaviour, no lint suppression. **Every router from here on should use the `Annotated`
form** — this is the first task that had reason to write a dependency, so it sets the pattern.
