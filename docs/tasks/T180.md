# T180 — The session endpoints

**Task**: Implement the sign-in, sign-out, and current-session routes in
`backend/app/users/router.py`.

## The project's first HTTP endpoints

Until this task, `register_routers()` in `app/main.py` was an empty function and the application served
nothing but `/openapi.json`. Three routes now exist, and they are the three the contract gained in T177:

```
POST   /auth/session   sign in  -> 200 + Set-Cookie
GET    /auth/session   whoami   -> 200 { username, expires_at }
DELETE /auth/session   sign out -> 204
```

One path, three verbs, because a session *is* a resource: you create it, read it, and delete it. There
is no `/auth/login` or `/auth/logout` — those would be the same two operations wearing verbs in their
paths.

Everything they need already existed. The router composes `authenticate`, `create_session`, and
`invalidate_session` from `app/users/auth_service.py` (T020), `CurrentUser` and `SESSION_COOKIE_NAME`
from `app/dependencies.py` (T021), `signin_rate_limit()` from `app/common/limits.py` (T179), and
`AuthenticationError` rendered by the middleware from T014. The whole file is 34 statements.

## Why `POST` returns nothing useful

```python
return SessionResponse(username=session.username, expires_at=session.expires_at)
```

No token. FR-079 requires secrets to be unreadable by the client, and a JSON body is readable by any
script on the page — including anything injected. The token goes out in one place only:

```python
response.set_cookie(..., httponly=True, samesite="lax", path="/")
```

`HttpOnly` is the entire reason this is a cookie rather than a bearer token. A test takes the token out
of the cookie jar and asserts it does not appear anywhere in the response text, on both `POST` and `GET`.

`max_age` is derived from the session itself — `expires_at - created_at` — rather than read from
configuration a second time, so the cookie's lifetime cannot drift from the session's own deadline.

`Secure` is absent, deliberately and conditionally. This release serves plain HTTP on loopback, and
FR-081 defers transport security. The contract records that the flag becomes mandatory alongside
`ALLOW_REMOTE_EXPOSURE`, because without it the cookie travels in clear text — making it a contract and
code change rather than something an operator can forget while flipping a deployment flag.

## Every failure is the same failure

```python
if not authenticate(credentials.username, credentials.password):
    logger.info("sign-in refused")
    raise AuthenticationError("Those sign-in details are not correct.")
```

Wrong password, unknown username, and a deployment with no `AUTH_PASSWORD_HASH` configured all land
here. The test does not merely check each for `401` — it compares the three response bodies and asserts
there is exactly one distinct value between them. The first pair being distinguishable would let a
caller enumerate usernames; the third leaks that a deployment has no credential at all, which is the
state every fresh checkout is in.

`authenticate` already does the constant-time comparison and evaluates both halves before combining
them, so the *timing* does not leak what the response refuses to.

The log line records that a sign-in was refused and nothing else — no username, no attempted password,
no indication of which check failed.

## Sign-out is not behind `CurrentUser`

This is the design decision most likely to look like an oversight, so: it is deliberate.

```python
session_token: Annotated[str | None, Cookie(alias=SESSION_COOKIE_NAME)] = None,
```

Sign-out reads the cookie directly instead of depending on `CurrentUser`. Two reasons:

1. Signing out with an *already expired* session must succeed. Behind `CurrentUser` it would `401`,
   which is a confusing answer to "end my session" — the session is, after all, ended.
2. Someone discarding a token they believe is compromised must never be refused because the token turned
   out to already be invalid.

So it returns `204` whether or not the token named a live session, which also makes it idempotent. A
`404` for an unknown token would confirm which tokens are real and turn sign-out into an oracle.

The cookie is cleared either way, so a dead token is not resent on every later request.

## `GET` exists for the SPA's cold start

The frontend is client-side only (R10). On every fresh load it has to decide whether to render the
sign-in screen or the application, *before* it fetches anything. Without this endpoint its only way to
find out is to fire a real data request and interpret the `401`, so every unauthenticated visit would
begin with a failed request against an unrelated route.

## Two things this task also changed

**`app/main.py`** now registers the router, and its docstring no longer claims the first router arrives
with T058.

**`tests/unit/test_app.py`** had a test named `test_no_endpoints_are_exposed_yet`, which was true right
up until this task. It is now `test_only_contracted_endpoints_are_exposed`, asserting the generated
OpenAPI schema contains exactly `/auth/session`. Asserting against the schema rather than the route
table is the better test anyway: that schema is what the frontend and the docs are written against, so
it is the surface the contract is a contract for. It still fails if anyone adds an uncontracted endpoint
— including a convenience health check.
