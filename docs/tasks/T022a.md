# T022a — Contracting the session endpoints

**Task**: Amend the API contract with the session endpoints in
`specs/001-reddit-audience-intelligence/contracts/rest-api.md`.

## Why this task exists at all

T017–T022 built everything needed to *carry* a session — hashed credentials, expiring and invalidatable
sessions, the `CurrentUser` dependency, per-caller rate limits. None of it built a way to *get* one.

`contracts/rest-api.md` said "all endpoints require an authenticated session" and then contracted no
endpoint that issues a session. So `CurrentUser` was unsatisfiable over HTTP: the only way to obtain a
session was to call `create_session` from inside the process. The first protected route, T058, would
have had nothing to authenticate against.

The gap was flagged in `docs/tasks/T021.md` rather than quietly patched, because Constitution III makes
this contract the single source of truth for the HTTP surface and forbids shipping an endpoint it does
not describe. That rule points at exactly this task: the contract changes first, in its own change set,
and the code follows in T022c–T022d.

## The three endpoints

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/auth/session` | Sign in; sets the `HttpOnly` session cookie |
| `DELETE` | `/auth/session` | Sign out, invalidating the session immediately |
| `GET` | `/auth/session` | The current session's username and expiry |

One path, three verbs. A session is a resource: you create it, you delete it, you read it. That is
also why there is no `/auth/login` and no `/auth/logout` — verbs in paths would be the same two
operations wearing different names.

`GET` is the one that could be argued away, and it earns its place: the frontend is a client-side-only
SPA (R10), so on every cold load it has to work out whether it is signed in *before* it renders. Without
this endpoint its only way to find out is to fire a real data request and interpret the `401`, which
means every unauthenticated visit starts with a failed request against an unrelated route.

## The exemption is written down and closed

The contract's `Auth` paragraph now says these three endpoints are exempt from requiring a session, that
the list is exhaustive, and that no other endpoint may be exempted without amending the file.

Stating it that way matters more than it looks. "All endpoints require a session, except the obvious
ones" is how an auth surface quietly grows a second unauthenticated route, then a third. An exhaustive
list makes any future exemption a visible edit to a source-of-truth document.

## What the contract pins about failures

The interesting part of a sign-in endpoint is not the success path.

**Every failure looks identical.** A wrong password, an unknown username, and an unconfigured
`AUTH_PASSWORD_HASH` all return the same `401` `not_authenticated` with the same message. The first two
being distinguishable would let a caller enumerate usernames. The third is subtler: "no credential is
configured on this deployment" is a genuinely useful thing for an attacker to learn, and it is precisely
the state a fresh checkout is in.

**`DELETE` returns `204` whether or not the session existed.** A `404` for an unknown token would
confirm that other tokens are live, which turns sign-out into an oracle. It is idempotent as a
consequence rather than by design.

**The token appears only in `Set-Cookie`, never in a response body.** FR-079 requires secrets to be
unreadable by the client, and a body is readable by any script on the page; an `HttpOnly` cookie is not.

**`Secure` is deliberately absent, with a condition attached.** This release serves plain HTTP on
loopback and FR-081 defers transport security to the deployment layer. But a cookie without `Secure`
travels in clear text, so the contract records that the flag becomes mandatory the moment
`ALLOW_REMOTE_EXPOSURE` is used — making it a change to this contract and to the route, not something
an operator can forget while flipping a deployment flag.

**Repeated failures are rate-limited**, keyed on the calling client rather than on a session, because
sign-in is by definition where no session exists yet. FR-081 defers *network-level* brute-force
protection; an in-process counter is application-level, costs one Redis `INCR`, and stays.
