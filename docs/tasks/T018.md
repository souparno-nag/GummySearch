# T018 — The loopback-by-default bind guard

**Task**: Implement the loopback-by-default bind guard that refuses a non-local interface without the
explicit exposure flag in `backend/app/main.py`.

## What this adds

Four things in `main.py`, plus one setting.

| Name | Role |
|---|---|
| `UnsafeBindError` | Raised to abort startup |
| `is_loopback(host)` | Decides whether an address is local |
| `resolve_bind_host(argv)` | Works out which interface is about to be bound |
| `assert_bind_allowed(host, *, allow_remote_exposure)` | The rule itself |

`create_app()` calls the guard as its first statement, and `settings.app_host` (`APP_HOST`, default
`127.0.0.1`) is the configuration fallback.

## The design decision that matters

The naive implementation reads a setting called something like `APP_HOST`, checks it, and stops. It
would pass a test suite and protect nothing, because of how the server is actually started.
`quickstart.md` says:

```bash
uvicorn app.main:app --reload
```

Nobody exposing this application edits a setting. They type `uvicorn app.main:app --host 0.0.0.0`. A
configuration-only guard would read `APP_HOST`, find the loopback default sitting there untouched,
approve it, and watch uvicorn bind every interface anyway.

So `resolve_bind_host()` **reads the command line first** and falls back to configuration:

```python
for index, argument in enumerate(arguments):
    if argument == "--host" and index + 1 < len(arguments):
        return arguments[index + 1]
    if argument.startswith("--host="):
        return argument.split("=", 1)[1]
return settings.app_host
```

Both spellings uvicorn accepts are handled, and a trailing `--host` with nothing after it falls
through to the default rather than crashing — malformed arguments are uvicorn's to complain about.

## Why the guard fails closed

`is_loopback()` returns `False` for anything it does not positively recognise, including hostnames
that would need DNS:

```python
try:
    return ipaddress.ip_address(candidate).is_loopback
except ValueError:
    return False
```

Two reasons, and the second is the real one. Constitution IV forbids tests touching the network, so a
resolving guard could not be tested properly. But more importantly, a resolved name is not a stable
fact — it can change, and it can be influenced by whoever controls the resolver. A guard whose verdict
depends on an answer someone else supplies is not a guard. Refusing what it cannot verify is the
correct bias for a control whose failure mode is silent internet exposure.

It does handle the whole `127.0.0.0/8` block rather than just `127.0.0.1`, along with `localhost`,
`::1`, and the bracketed `[::1]` form.

## Why `UnsafeBindError` is not an `AppError`

Every exception in `app/common/exceptions.py` exists to be turned into an HTTP response by the shared
middleware. This one never will be: it fires before the server is listening, so there is no request to
answer. It subclasses `RuntimeError` and lives beside the guard.

The project convention — raise typed exceptions from `common/`, do not invent domain subclasses there
— is about errors that reach a client. This is a startup abort, a genuinely different category, and
filing it under `common/exceptions.py` would imply a status code and an envelope that will never
exist.

## The refusal message

FR-052 requires errors to state what failed and what to do next, and there is no reason a startup
failure should be exempt:

```text
Refusing to start: '0.0.0.0' is not a local address, and ALLOW_REMOTE_EXPOSURE is not set.
This application is intended to run on your machine only. To bind it anyway, set
ALLOW_REMOTE_EXPOSURE=true in .env — and read FR-081 first, because transport security,
abuse protection, and monitoring are not part of this release. To keep it local, start it
on 127.0.0.1.
```

It names the host, names the setting, and points at FR-081 — because someone reaching for that flag is
exactly the person who should know which protections this release deliberately does not have.

The permitted case is not silent either. Binding a non-local interface with the flag set logs a
warning, so there is one line in the log explaining why the tool is reachable from off the machine.

## Verified against a real server

The test suite covers the logic; these were run against actual uvicorn, because a guard that only
works in tests is the failure mode this task exists to avoid:

| Command | Result |
|---|---|
| `uvicorn app.main:app --host 0.0.0.0` | `UnsafeBindError`, process exits |
| `uvicorn app.main:app` | Starts; `/openapi.json` returns `200` |
| `ALLOW_REMOTE_EXPOSURE=true uvicorn app.main:app --host 0.0.0.0` | Starts on `0.0.0.0`, warning logged |

The third row is **SC-020 demonstrated**: exposing the application took a configuration change and no
code change. That success criterion is now satisfiable by running the command rather than by argument.
