# T005 — docker-compose.yml for PostgreSQL (pgvector) and Redis

**Task**: Create `docker-compose.yml` at repo root with PostgreSQL plus the pgvector extension and
Redis.

## What problem is this solving?

This app needs two supporting pieces of infrastructure to run: a database (PostgreSQL) and a fast
in-memory store used for caching and background job queuing (Redis). Rather than installing these
directly on your machine — which gets messy across projects, and different projects wanting different
versions — **Docker** lets you run each one in its own isolated, disposable container, and
**docker-compose** is a tool that starts a whole group of related containers together with one
command, using a single YAML file to describe what each one needs (which image, which ports, which
settings).

## What is pgvector, and why does Postgres need it?

Later in this project, posts get converted into "embeddings" — long lists of numbers that represent
the *meaning* of the text, used for the "Ask a question" and semantic-alert features. Storing and
efficiently searching those embeddings needs special database support that plain PostgreSQL doesn't
have. **pgvector** is an extension that adds that capability directly inside PostgreSQL, so there's no
need for a second, separate "vector database" service — one database does both jobs. `docker-compose.yml`
uses the `pgvector/pgvector:pg16` image, which is just PostgreSQL 16 with that extension already
installed and ready to be turned on (turning it on for a specific database happens later, in T035's
migration — this task only makes sure the extension is *available*).

## What's in the file

Two services:

- **`postgres`** — the database. Configured with a username/password/database name (with sensible
  defaults, overridable via a `.env` file later), a persistent volume so data survives a container
  restart, and a **health check** — a command Docker runs repeatedly (`pg_isready`) to know whether
  Postgres has actually finished starting up and is ready to accept connections, not just that the
  container process exists.
- **`redis`** — the cache/queue. Same pattern: persistent volume, and a health check (`redis-cli ping`).

Both services publish their ports only on `127.0.0.1` (`"127.0.0.1:5432:5432"` etc.) rather than on
all network interfaces. This means only programs running on your own machine can reach them — nothing
on your local network can connect to your database, matching the project's "local machine only by
default" security posture (Constitution's FR-078/R17) even though that rule is really about the web
app itself.

## The port conflict we hit, and why

When you first ran `docker compose up -d`, Docker refused to start the Postgres container: something
was already listening on port 5432, which is PostgreSQL's standard port. We tracked it down with
`ss -ltnp | grep 5432`, which showed a **native** PostgreSQL 16 service already installed and running
directly on your machine (`postgresql@16-main.service`), unrelated to Docker — probably left over from
an earlier setup. Docker containers that "publish" a port are really just asking the host machine to
forward that port to the container, so if something on the host already owns it, the container can't
bind to it.

You chose to stop and disable that native service (`sudo systemctl disable --now postgresql`) rather
than have the container use a different port — since this project's design (see `quickstart.md`)
assumes the database lives in Docker on the standard port, this keeps things matching the documented
setup instructions exactly, with no special-cased port number to remember later.
