# T012 — Redis connection pool (`common/redis.py`)

**Task**: Implement the Redis connection pool in `backend/app/common/redis.py`.

## What problem is this solving?

The constitution says the Reddit data layer must cache, so the application isn't re-fetching the same
subreddit listing every time someone opens a feed. Reddit's API is rate-limited and slow relative to
local storage; a cache is what makes the "under 500 ms cached feed read" budget achievable at all.

**Redis** is that cache — an in-memory key/value store, already running as a container from T005. This
task builds the connection to it. It does *not* build the caching itself: deciding what gets cached
and for how long is `app/reddit/cache.py` (T026), which will import the client made here.

## Redis has two jobs in this project — this module owns one of them

Worth being explicit, because it's a common source of confusion:

1. **Cache** in front of the Reddit API — application-side, and what this module provides.
2. **Broker** for Celery, the background job system — the queue that holds "please ingest this
   subreddit" messages until a worker picks them up.

`workers/celery_app.py` (T036) will configure Celery's own connection from the same
`settings.redis_url`. It deliberately does **not** share this pool. A web process and a worker process
have different lifetimes and different concurrency, and Celery manages its broker connections with its
own logic; wiring them together would couple two things that only coincidentally point at the same
server.

## What's actually in the file

### `pool` — the connection pool

Same reasoning as the database engine in T011: opening a TCP connection costs real time, so a pool
keeps a set of them open and hands one out per command. Three settings are non-default:

- **`max_connections=20`** — a bound. This is generous for a single-user tool, and the point of
  bounding it is diagnostic: if the code ever leaks connections without returning them, the pool
  exhausts and raises, which is a bug you can find. An unbounded pool hides the same leak until Redis
  itself refuses new connections, much later and much further from the cause.
- **`health_check_interval=30`** — Redis's equivalent of the database's `pool_pre_ping`. A connection
  that has sat idle longer than 30 seconds gets pinged before it's reused, so one the server quietly
  dropped (container restart, idle timeout) is replaced transparently instead of failing a request
  with a confusing error.
- **`decode_responses=True`** — makes the client return `str` instead of `bytes`. Redis speaks bytes
  natively, and by default the client hands them straight through, so every call site would have to
  remember `.decode()`. Everything this project stores in Redis is text (JSON-serialized Reddit
  listings), so decoding once at the client is simpler and removes a whole category of
  `bytes`-vs-`str` bug.

The URL comes from `settings.redis_url`, not from the environment directly — `app/config.py` remains
the only module that reads `.env`.

### `redis_client` — the shared client

Constructing the client opens no socket. Like the database engine, the first connection is made lazily
on the first actual command, so importing this module performs no I/O.

### `get_redis()` — and why it differs from `get_session()`

This is the interesting design point of the task. `get_session()` in T011 is a generator that yields a
**fresh session per request** and closes it afterwards. `get_redis()` returns the **same shared
client** every time.

The difference is that a database session carries state: it holds an open transaction, tracks which
objects have been modified, and must be committed or rolled back and then disposed of. Two requests
sharing one session would see each other's uncommitted changes.

A Redis client carries none of that. Each command is independently atomic — there is no transaction to
open and nothing to clean up — so a single client is safe to share across every concurrent request.
Worse, giving each request its own would be actively harmful: closing it at the end of the request
would tear down the shared pool for everyone else. Hence a plain `return`, not a `yield`.

### `close_redis()`

Closes the client and disconnects every pooled connection, called on application shutdown so the
process doesn't exit leaving connections open on the Redis server. It does both steps in order —
closing the client alone leaves the pool holding sockets.

## Tests

`backend/tests/unit/test_redis.py` — seven tests, none of which open a socket:

- the pool points at the host and port from `settings.redis_url` (proving the module doesn't re-read
  the environment itself)
- pooled connections are health-checked before reuse
- the pool is bounded
- responses are decoded to text, so callers never handle raw bytes
- every caller shares one client, and `get_redis()` is stable across calls
- the client is bound to the shared pool rather than having quietly built its own
- shutdown closes the client *and then* drains the pool, in that order

Coverage of `app/common/redis.py` is 100%.

## Dependency change

`requirements.txt` gained an explicit `redis` line. The package was already installed — `celery[redis]`
pulls it in — but it was a *transitive* dependency, present only as a side effect of Celery's needs.
Now that application code imports `redis.asyncio` directly, it is a **direct** dependency, and
`CLAUDE.md` requires a dependency be declared in the same change that imports it. Concretely: if Celery
were ever swapped out or changed its extras, a transitive-only `redis` could vanish and break the cache
for reasons that have nothing to do with the cache.

This needs no constitutional amendment — Redis is already part of the committed stack; only the way
it arrives changed.

Checked against the running container (`gummysearch-redis-1`), not just the unit suite:


That confirms the round trip works end to end, `decode_responses` really does yield a `str`, key
expiry is honoured (which T026 depends on entirely), the connection is returned to the pool rather
than leaked after the command, and shutdown is clean.
