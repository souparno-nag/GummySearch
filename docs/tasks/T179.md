# T179 — A rate limiter for the endpoint with no caller yet

**Task**: Implement the client-keyed rate limiter for unauthenticated endpoints in
`backend/app/common/limits.py`.

## The problem with the limiter T022 built

T022's `rate_limit(...)` keys each allowance on the signed-in caller:

```python
async def enforce(user: CurrentUser, redis: ...) -> Allowance:
    return await consume_rate_limit(redis, bucket=bucket, subject=user.username, ...)
```

That is right for the endpoints it was written for — one caller cannot spend another's Ask allowance,
and an unauthenticated flood is refused at the door instead of consuming the real user's budget.

It is also structurally unusable on sign-in. `CurrentUser` resolves *before* the limiter counts, so
attaching it to `POST /auth/session` would refuse every request with a `401` before anyone could sign
in. The endpoint that most needs a limit is the one endpoint whose whole purpose is that no session
exists yet.

## What this adds

`signin_rate_limit()` — same counting, different key:

```python
subject = request.client.host if request.client else "unknown"
```

`consume_rate_limit` is reused **unchanged**. There is one counting implementation, one fixed-window
algorithm, one place where the Redis key format lives. Only the choice of subject differs.

Sign-in gets its own bucket (`SIGNIN_BUCKET = "signin"`), so exhausting sign-in attempts cannot refuse a
signed-in caller's Ask allowance, and a flood of sign-in attempts is visible as itself rather than
buried among paid-call counters.

## `X-Forwarded-For` is deliberately ignored

The obvious "improvement" here is to read `X-Forwarded-For` so the limit survives a reverse proxy. That
header is set by the client. Honouring it would let a caller send a different value on every attempt,
mint a fresh subject each time, and walk straight through the limit — a limiter that is trivially
bypassed is worse than none, because it reads as protection.

Behind a proxy this implementation therefore keys every caller to the proxy's address, which is
strictly a deployment concern. FR-081 defers exactly that layer to a later release; it does not license
trusting a spoofable header now. A test asserts the header is ignored, so nobody "fixes" this by
accident.

There is a matching fallback for `request.client` being `None`, which happens on ASGI transports that
report no peer: such callers share one allowance. That errs toward refusing rather than toward an
unbounded endpoint.

## The allowance is read per request

```python
requests=settings.signin_rate_limit_requests,
window_seconds=settings.signin_rate_limit_window_seconds,
```

Read inside `enforce`, not captured when the route is declared. `paid_call_rate_limit` reads
configuration at decoration time, which means changing the number needs the application rebuilt.
FR-080's reasoning applies here too — a control that is awkward to adjust is one an operator eventually
works around — and the request-time read also lets a test set the allowance without constructing a new
app.

New settings, documented in `.env.example`: `SIGNIN_RATE_LIMIT_REQUESTS` (10) and
`SIGNIN_RATE_LIMIT_WINDOW_SECONDS` (300). They are separate from the paid-call defaults because the
profile is different: signing in costs no money, but it is the only endpoint an unauthenticated caller
can reach repeatedly. Ten attempts per five minutes is unremarkable for someone mistyping a password
and useless for guessing one.

## Is this even in scope?

FR-081 lists "network-level abuse or brute-force protection" as explicitly *not* required in this
release. It would be easy to read that as excluding this.

It does not, on two grounds. The measure here is application-level and costs one Redis `INCR` — it is
not the network appliance FR-081 is deferring. And FR-079 requires that no security measure lean on the
loopback-only bind, which is precisely what "we are not reachable, so unlimited password attempts are
fine" would be doing.
