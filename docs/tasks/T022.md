# T022 — Server-side rate limiting

**Task**: Implement server-side rate limiting applied to every paid-call endpoint in
`backend/app/common/limits.py`.

## What problem is this solving?

FR-080 says request rate limits must be enforced

> on the server as controls in their own right, never as interface conveniences, so that they remain
> effective if the deployment is later exposed.

and `contracts/rest-api.md` supplies the test of whether that was achieved:

> A client that omits the check must not be able to exceed them.

That sentence rules out the common shape — an endpoint returning `X-RateLimit-Remaining` and trusting
the frontend to stop. Here the limiter refuses, from a dependency that runs before the route body, and
a caller using `curl` in a loop is bound exactly as much as the SPA.

The immediate value is not abuse protection; it is a runaway loop. Groq's free tier is a *rate* limit,
and R1 is explicit that zero marginal cost does not make the ceiling optional. A retry bug that fires
a thousand Ask requests would exhaust the day's allowance in seconds, and nobody would find out until
the product stopped answering.

## What it exposes

| Name | Role |
|---|---|
| `consume_rate_limit(redis, ...)` | The counter. Returns an `Allowance` or raises |
| `rate_limit(bucket, requests=, window_seconds=)` | Dependency with explicit numbers |
| `paid_call_rate_limit(bucket)` | Dependency using the configured default |
| `Allowance` | What is left, and when it returns |

Attached to a route like this:

```python
@router.post("/audiences/{id}/ask", dependencies=[paid_call_rate_limit("ask")])
```

## The counting strategy, and its honest trade-off

A **fixed window**. The window index is part of the Redis key:

```text
ratelimit:ask:researcher:29780949
```

so a new window is simply a new key, and expiry needs no separate bookkeeping — the old key ages out
on its own TTL. `INCR` creates the key at 1, and `EXPIRE` is set only on that first request of a
window. Setting the TTL on every request would be the subtle bug: a steady stream of calls would keep
pushing the deadline out and the counter would never reset.

**The trade-off, stated plainly**: a caller can spend a full allowance at the very end of one window
and another at the start of the next, briefly achieving twice the nominal rate. A sliding-window log
fixes that, at the cost of storing a timestamp per request.

It is not worth it here. This limit exists to stop runaway loops and bound cost, not to smooth traffic
into a shared service, and a brief 2× burst from a single-user tool harms nothing. Recorded rather
than glossed over, because "fixed window" without this paragraph reads as though the boundary case
went unnoticed.

## Two dimensions of isolation

**Per caller.** The subject is part of the key, so one caller cannot consume another's allowance. At
single-user scale this looks redundant; it stops being redundant the moment FR-078's exposure flag is
used, which is precisely the scenario FR-080 says these controls must survive.

**Per bucket.** Exhausting `ask` must not also block `search`. They are separate controls over
separate costs, and collapsing them would make one expensive feature disable a cheap one.

Because the allowance is keyed on the caller, **authentication resolves first**. That falls out of the
dependency graph rather than being arranged, and it has a useful consequence: an unauthenticated flood
is refused at the door with a 401 and never touches the real user's counter. A test pins it.

## The refusal says how long to wait

```text
You have made too many requests. Try again in 29 seconds.
details: {"retry_after_seconds": 29, "limit": 3}
```

FR-052 requires errors to state what the user can do next, and "try again later" is not that. The
number is in `details` for the client and in the message for a human. It comes back through the shared
envelope from T014 like every other error, so a 429 needs no special handling.

## Configurable, deliberately

`paid_call_rate_limit` reads `RATE_LIMIT_REQUESTS` and `RATE_LIMIT_WINDOW_SECONDS` from configuration
rather than hard-coding them. FR-080 treats these as real controls, and a control that requires a code
change to adjust is one an operator eventually disables instead of tuning. Endpoints with their own
cost profile can still call `rate_limit` with explicit numbers.

Defaults are 60 requests per 60 seconds — generous for one person working normally, low enough that a
runaway loop hits it in a second.

## Scope: this is the rate half of FR-080

FR-080 names two controls, and this module is one of them. The **spend ceiling** (FR-046) is a
different control with a different unit — money, not requests — and arrives with `app/ops/` at T031.
They are separate because they fail differently: a rate limit protects the service from volume, a
spend ceiling protects the wallet from a single expensive call. One does not imply the other, which is
why the requirement lists both.

## Verified against a real server

Beyond the tests, run against the live Redis container:

```text
request 1: allowed, remaining=2
request 2: allowed, remaining=1
request 3: allowed, remaining=0
request 4: refused -> You have made too many requests. Try again in 29 seconds.
key: ratelimit:smoke:researcher:29780949 | ttl: 60
next window: allowed, remaining=2
```

Confirming what the in-memory fake asserts: the counter refuses at the limit, the key carries a TTL so
counters cannot accumulate, and the allowance returns with the next window.
