# T022b — Failing tests for the session endpoints

**Task**: Write failing tests for the session endpoints in
`backend/tests/integration/test_auth_routes.py`.

## The project's first integration test

Every test before this one lived in `backend/tests/unit/`. This one belongs in
`backend/tests/integration/` because a single request through `POST /auth/session` crosses four
modules — the users router, `app/dependencies.py`, the limiter in `app/common/limits.py`, and the error
middleware — and Constitution IV requires integration tests for anything crossing a module boundary.

It drives the **real application** from `create_app()`, not a hand-built `FastAPI()` with the router
attached. That matters because a good half of what can break here is wiring: a router that is never
registered in `register_routers()`, or registered under a path the contract does not name, would pass
every unit test written against the route functions directly.

## The credential comes from the fixture, not from `.env`

```python
PASSWORD_HASH = hash_password(PASSWORD)  # module level: scrypt is slow on purpose

@pytest.fixture
def configured(monkeypatch):
    monkeypatch.setattr(settings, "auth_username", "researcher")
    monkeypatch.setattr(settings, "auth_password_hash", PASSWORD_HASH)
```

A fresh clone has `AUTH_PASSWORD_HASH` empty, so a suite that signed in with the developer's real
credential would fail for everyone else and, worse, pass or fail depending on a file that is
gitignored. Hashing happens once at module import because `hash_password` is deliberately expensive
(scrypt at roughly 16 MiB); per-test hashing would buy nothing and cost a second of suite time.

## What is actually being pinned

The success path is three assertions. Almost everything else is about what a failure must not reveal,
which is where a sign-in endpoint is either right or quietly wrong:

- **All three refusals are byte-identical.** Wrong password, unknown username, and unconfigured
  `AUTH_PASSWORD_HASH` are compared against each other, not just each checked for `401`. The first pair
  being distinguishable would let a caller enumerate usernames; the third leaks that this deployment has
  no credential set at all, which is exactly the state a fresh checkout is in.
- **A malformed body is `422`, not `401`.** A missing field is the caller's bug. Answering it with
  "unauthorized" would hide a client defect behind an auth failure indefinitely.
- **The token never appears in a response body** — asserted by taking the token from the cookie and
  searching the body text for it, on both `POST` and `GET`.
- **The cookie is `HttpOnly` and `SameSite=Lax`**, read off the raw `Set-Cookie` header rather than the
  parsed cookie jar, because the flags are the point and a jar discards them.
- **Sign-out is idempotent and clears the cookie.** `204` with no session, `204` twice, and a
  `Set-Cookie` that empties the value so a dead token is not resent on every later request.
- **Sign-out deletes one key.** Redis also holds the Reddit cache, which costs real quota to rebuild, so
  the test seeds a cache key and asserts it survives.
- **The limit counts attempts, not failures.** One test exhausts the allowance with failures, another
  with a *success*. A limiter that only counted failures would be trivially evaded by a caller who does
  not care about the outcome.

## Honest note on "failing first"

20 of the 23 tests fail, all with `404` — the routes do not exist yet. Three pass vacuously: a `404`
response also sets no cookie, mentions no hashing scheme, and touches no Redis key. They are kept
rather than contrived into failing, because their value is as regressions after T022d lands; padding
them with an extra assertion just to make them red first would be theatre.
